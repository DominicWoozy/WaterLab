# 折射修正后的性能实验

2026-09-11。容器接触修正已推送为 `f1937e4ddc0a644f054e4aa821ab8f14de57fa98`，GitHub Pages 工作流 34558698069 成功。本轮运行代码仅采用下述着色顺序优化，其他方案保留为独立实验。

## 最终运行代码

只调整着色执行顺序，未采用密度范围缓存：

- 相机光线命中水面时，直接计算水体颜色；不再提前计算随后会被覆盖的地面/鸭子颜色。
- 透射路径耗尽预算并使用环境近似时，不再先查询场景再覆盖该结果。
- 没有改变折射、全反射、吸收、法线、表面步进、粒子数、分辨率、焦散或容器接触处理；没有增加通道、纹理和缓存。

这借鉴提前终止/避免无贡献工作的方向，而非完整移植某篇体渲染系统。参考 [Krüger / Westermann, Acceleration Techniques for GPU-based Volume Rendering (2003)](https://www.cs.cit.tum.de/cg/research/publications/2003/acceleration-techniques-for-gpu-based-volume-rendering/)。本项目的具体改动是确定输出被覆盖后省掉着色，不以不透明度阈值截断真实透射。

## 性能与图像验证

M3 Pro / 原生 Metal WebGPU / 50k / 1250×800 / 硬件浮点过滤 / 反射与焦散开启。每组恢复相同粒子、鸭子、浮力反馈和模拟时间，新旧着色器交替运行。240 帧去掉前 20 帧，各 110 帧，GPU 时间戳均值：

| 场景 | 水体绘制：基线 → 本地 | 阶段减少 | 整帧 GPU：基线 → 本地 | 整帧减少 |
| ---- | --------------------: | -------: | --------------------: | -------: |
| 平静 |      2.179 → 2.021 ms |     7.2% |    28.891 → 28.661 ms |     0.8% |
| 浪花 |      4.322 → 4.238 ms |     1.9% |    22.950 → 22.901 ms |     0.2% |

这是小幅改进，整帧差异接近运行波动，不能承诺用户能感到帧率上升。不同场景分开运行，GPU 频率/调度不同，不能用表格横向推断浪花比平静更便宜；只能比较每行内部交替结果。也不包含浏览器合成开销。原始摘要见 `experiments/deferred-water-results.json`。

`tests/webgpu-shading.mjs` 用完整生产着色器，对比旧的提前计算顺序和新顺序。256×192，俯视、侧视和无水场景，包含分离水层、悬空球体及真实鸭子网格。硬件过滤与手动三线性过滤下，所有输出像素的最大差值和 RMS 均为 **0**。这是原生 GPU 数值图像对比，没有浏览器视觉验收。

## 未采用的论文路线

依据 [Implicit KD-Trees (2005)](https://www.sci.utah.edu/~wald/Publications/2005/iso/tcgv.pdf) 的保守密度范围，以及 [Amanatides / Woo DDA (1987)](https://www.eecs.yorku.ca/~amana/research/grid.pdf)，实际实现并测试了下列方案。性能均包含当帧缓存构建，而非只计跳跃后的渲染。

| 实验                                  | M3 Pro 硬件过滤下的结果 | 决定   |
| ------------------------------------- | ----------------------- | ------ |
| 4³ 单元宏块，只用于透射               | 平静整帧约慢 0.5%       | 不采用 |
| 同时用于相机与透射光线                | 浪花整帧约慢 3.8%       | 不采用 |
| 8³ 单元宏块                           | 浪花整帧约慢 3.9%       | 不采用 |
| 4³ 宏块、增量 DDA、保留原浮点步进顺序 | 浪花整帧约慢 6.0%       | 不采用 |
| 复用末段物体交点，扩展透射结果结构    | 浪花整帧约慢 3.2%       | 不采用 |

手动三线性过滤下曾有约 2%～4% 的整帧收益，但绘制阶段的均值/中位数并不稳定。直接把多步推进合为一次乘加还造成约 0.0036 的个别输出差异；保留原浮点累加顺序后消除了这类可观测差异，但阶段性能优势缩小。因此本轮没有按设备开启该方案。

保守缓存使用 5³ 支撑节点覆盖 4³ 插值单元，包含共享边缘/角点，使用 f32 范围和向外余量。最终增量版本在 384 条生产光学路径、539 次界面事件上，界面次数/完成状态一致，最大数值差约 1.22e-5；完整合成测试图像最大差约 1.34e-7，两种过滤路径均通过。缓存约 0.234 MiB。问题是当前工作负载上未取得速度收益，而不是通过丢失表面来加速。

我的判断：硬件过滤已把密度采样做得很便宜；新增遍历状态和分支增加了着色器负担。没有硬件寄存器/占用率计数器数据，不能将寄存器压力认定为已证实的单一瓶颈。论文里的其他硬件、超大体数据与长光线收益不应直接套用。

## 实验复现

- `experiments/macrocell-attempt.patch` 保存最终增量 DDA 的完整原型补丁，针对干净的 `f1937e4`。请在隔离副本应用；它不是运行代码的一部分。
- 应用补丁后运行 `experiments/macrocell-optics.mjs` 检查保守范围、共享支撑节点、插值值、光线、图像与清空缓存。`UNFILTERED=1` 覆盖手动过滤。
- `experiments/macrocell-frame-benchmark.mjs` 包含缓存构建的配对整帧测量，`BASELINE_SHADER` 指向保留同目录依赖的基线 `render-shaders.ts`；`SCENE=rough` 选择浪花。
- `experiments/cached-receiver.mjs` 与对应 frame benchmark 是交点复用实验。所有候选结果摘要保存在 `experiments/macrocell-results.json`。
- `experiments/deferred-water-frame-benchmark.mjs` 在同一基线着色器上变换计算顺序，复现本轮保留的小优化；同样通过 `BASELINE_SHADER` 指定基线。

后续若再推进更大优化，应先获取分支/寄存器/纹理等待的细分证据，再决定是否值得把光线求交与着色拆成独立计算阶段。现有测试不支持“仅增加缓存就能明显提速”的结论。
